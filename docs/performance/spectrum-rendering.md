# 频谱流畅度与资源优化（2026-10-28）

## 范围与方法

基线提交：`9bfc97c`（main，第一里程碑质量整改完成）。采用 ECC benchmark-optimization-loop：先测旧发布版，再按绘制提交、频谱投影／过渡、批量绘制三个假设逐项比较；批量绘制未获益即撤回。保持音频采样、FFT 长度、分析频率、VU 模型、校准和编码算法不变。本轮不做架构重写或降低绘图分辨率。

用户允许本轮前台及麦克风测试，明确禁止 Computer Use。实窗检查通过 PowerShell + Windows UI Automation 选取页签，使用内部麦克风共享 RAW 监看；没有播放声音或开始录制。每轮仅关闭探针自己启动的进程，不强制终止其他应用。

硬件：Ryzen AI 9 H 365（10 核 / 20 线程）、Radeon 880M、约 31.1 GiB 可见内存，图形驱动 32.0.12033.1030；QueryDisplayConfig 读取窗体所在屏幕当前 120 Hz。输入为 48 kHz、float32、双声道。

用户提供的 1080p60 手机视频已抽帧检查频谱段。它能支持卡顿的观察，不能证明应用达到 120 fps；测量采用应用内部绘制计数。不同运行的麦克风环境、JIT、调度、GPU 和系统负载并非完全一致，不能将这些短测当成受控的整机性能认证。

## 原因与实现

1. 原有 `CompositionTarget.Rendering → CanvasControl.Invalidate → Draw` 链路，日志中实际 Draw 长期只有刷新请求的一半。旧版请求 83.2 / 87.0 次每秒，对应 Draw 41.6 / 43.6 次每秒。应用的请求频率并不等于真正绘制频率。
2. 换用 Win2D `CanvasSwapChainPanel` 和透明预乘 alpha 双缓冲交换链，在合成回调中绘制、`Present(0)` 提交；避免再排队请求 CanvasControl 重绘，也不在 UI 线程额外等待一次垂直同步。所有绘图和视图状态仍在 UI 线程，不跨线程枚举音高历史。
3. 移除合成回调上的第二重时间门限。回调本身已经由合成器调度，略早到达的有效帧不应再被丢弃。后台屏幕探测保留作诊断；最小化不绘制，音频和写盘继续。
4. 频谱像素桶的频率映射、二分定位只在采样频点或边界改变时重建；复用三个视觉点数组。高频仍取桶内峰值，低频仍作功率插值，金色曲线／条纹／辉光保留。
5. 曲线从当前可见形态向新数据插值，过渡时长由相邻真实音频帧间隔决定（视觉保护范围 12–60 ms），代替固定 20 ms 后等待下一帧的停顿。只影响显示，不改变测量值。
6. SpectrumEstimator 复用内部功率暂存数组，20 / 250 ms 平滑系数每次分析仅各计算一次；已发布的 dB 数组仍各自独立，不能复用后改写旧快照。音高能量直接读窗口，不复制各声道窗口；环形窗口使用两段 Span.CopyTo，缩短采集锁内工作。
7. DPI 变化重建对应尺寸缓冲；图形设备丢失时释放交换链及缓存，下一帧重建。关闭释放自有设备、缓存和交换链。

参考：[微软 Win2D 交换链用法](https://learn.microsoft.com/en-us/windows/apps/develop/win2d/using-win2d-without-built-in-controls)、[DPI 与 DIP](https://learn.microsoft.com/en-us/windows/apps/develop/win2d/dpi-and-dips)。没有增加新的图形依赖。

## 实测记录

每个 live 探针预热 6 秒，随后采样 25 秒（首个旧版基线为 20 秒）。表中绘制率只取启动后的完整 10 秒窗口；日志第一条含首次启动／JIT，排除它。Present 计数表示应用成功提交帧，不等同逐帧测量显示器扫描输出。

| 版本 / 进程 | 稳定绘制或提交次数/秒 | 采样 CPU 秒 / 墙钟秒 | 工作集 MiB | 私有内存 MiB |
|---|---|---|---|---|
| 旧版首次，23684 | 43.4 | 17.08 / 20.02 | 305.4 | 211.0 |
| 旧版复测，44564 | 41.6、43.6 | 19.25 / 25.02 | 315.1 | 219.2 |
| 首个交换链，43052 | 82.9、102.4 | 22.78 / 25.01 | 361.7 | 272.0 |
| 交换链＋投影缓存／过渡，20504 | 113.9、94.3 | 21.64 / 25.02 | 345.5 | 257.2 |
| 同方案复测，29724 | 75.2、73.8 | 23.14 / 25.01 | 345.6 | 256.6 |
| 最终显式透明交换链，12468 | 118.2、114.2 | 20.47 / 25.02 | 345.6 | 254.9 |

改善在多次运行中出现，但并未证明始终稳定 120 fps。新版绘制更多帧，总 CPU 没有下降；最后一次较旧版复测多约 6% 进程 CPU 时间，工作集多约 30.5 MiB。`20.47 CPU 秒 / 25.02 秒` 约等于 0.82 个逻辑核心的累计工作量，不是整机 82% CPU，也不是 GPU 利用率。内存数字为进程快照，不包含完整 GPU 显存统计。本轮接受这项流畅度／缓冲资源交换，不声称实现所有资源指标同时降低。

### 独立分析微基准

固定 48 kHz、8192 点、双声道 440 / 550 Hz、峰值 0.2，预热 1000 次后测 5×1000 次。各次峰值均为 −17.03851 dBFS。

- 旧版每 1000 次分配：49,216,040 字节（首轮多少量计时初始化）。
- 新版：16,416,040 字节，减少约 66.6%；保留输出快照分配。
- 五轮中位耗时：旧版 469.32 ms，新版 420.98 ms；存在 JIT／调度异常值，不把约 10% 的短测差异外推为整个音频引擎提速比例。

### 撤回的试验

将逐像素渐变换成缓存纹理＋SpriteBatch：两段约 100.2 次/秒，但 25 秒 CPU 为 23.64 秒，未比原绘制获得明确收益，已完全撤回。保留现有外观和兼容路径，避免为名义上的“批量”增加复杂度。

## 复现

```powershell
./tools/build.ps1
& F:/Codex/.tools/portable-recorder/dotnet/dotnet.exe run --project tools/PortableRecorder.Audio.Benchmarks -c Release
./tools/measure-monitor.ps1 -AllowMicrophone -Mode 频谱 -Seconds 25 -Label spectrum -Screenshot
./tools/check-audio.ps1
```

live 脚本必须显式传 `-AllowMicrophone`，启动实际发布目录 EXE，使用 UI Automation 选择页签（无 Computer Use），输出到 `artifacts/monitor-performance/`。截图仅在 `-Screenshot` 时采集，会包含当时窗体所在屏幕区域，测试时不要遮住应用。运行前关闭已有测试实例，避免同时采集及后台负载污染结果。音频微基准不使用设备、桌面或网络。

原始本地证据：`artifacts/spectrum-perf/` 的 baseline-repeat / optimized-repeat、各 live JSON／日志／截图，以及 `artifacts/monitor-performance/final-spectrum-20261028-105101/`。这些文件按现有规则不进入 Git；上表保留可审阅的摘要。

## 验证边界

13 组 / 658 项断言全部通过（断言数不等于场景数或覆盖率）。音频全组回归覆盖 PCM、RMS／VU／FFT／音高、校准及录音边界、编码和故障生命周期；新增检查验证旧频谱快照不会因暂存复用而改变，并核对缓存系数的功率域回落值。WinUI 发布编译成功，实窗检查三种页签的显示、绘制、关闭和真实共享监看。另以无采集模式完成五轮抽屉开关及输入／文件选中检查。电平／音高短测期间有离线校验并行执行，只作功能检查，不用于性能对比。该检查不替代用户对运动手感的判断，也没有重新进行独占兼容、硬件拔插或长时录音验收。

跨屏／DPI 切换、显卡设备丢失恢复路径有实现保护，本轮没有人为触发驱动重置；不把源码检查写成实机验收。下一轮若仍有卡顿，应优先获取 UI / GPU 时间线并检查残余长帧，不能仅提高目标帧率或降低 FFT 精度掩盖问题。
